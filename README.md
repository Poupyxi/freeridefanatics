# RidersFanatics — UCI MTB World Cup DH kit tracker

Static site: one directory page + one detail page per rider, listing their
full race setup with "Shop" buttons for affiliate links. Design language is
adapted from hotcut.xyz (warm light background, wavy line-art decoration,
condensed headlines, mono labels, burnt-orange accent).

## Structure

```
scripts/sync_notion.py    — exports the read-only Notion model used by the site
scripts/sync_drive_images.py — mirrors the read-only Google Drive image library
import_images.py          — matches + resizes the synchronized Drive images
build.py                  — generator: core, rider, equipment and trust pages
build_seo_guides.py       — localized editorial guides + sitemap.xml + robots.txt
optimize_images.py        — responsive WebP variants + intrinsic image dimensions
data/notion/riders.json   — generated from Notion; do not hand-edit
data/notion/competitions.json — generated competition and result model
assets/css/style.css      — shared stylesheet
assets/js/site.js         — header, mobile nav, scroll reveal, FAQ, grid filters, equipment marquee
assets/img/riders/        — square avatars, generated by import_images.py
assets/img/riders-action/ — portrait action shots, generated by import_images.py
assets/img/equipment/     — product photos, generated by import_images.py
index.html                — generated, do not hand-edit
riders.html               — generated, do not hand-edit
riders/{slug}.html        — generated, do not hand-edit
equipment.html            — generated equipment directory
equipment/{category}.html — generated category datasets and rider links
guides/{language}/        — generated localized editorial SEO guides
sitemap.xml / robots.txt  — generated search-engine discovery files
```

Two read-only sources feed the deployed site: Notion is the only source of
structured rider, result, competition and equipment data; Google Drive is the
only source of images. The former Google Sheets importer remains only as a
legacy local utility and is never used by either deployment workflow.

## Updating the site

For a local Notion refresh, provide `NOTION_TOKEN`, export the current model,
then build:

```bash
python3 scripts/sync_notion.py
python3 build.py
```

Useful local checks:

```bash
python3 scripts/validate_rider_snapshot.py data/notion/riders.json
python3 tests/notion_only_source.py
python3 tests/result_status_logic.py
python3 build.py
python3 optimize_images.py          # rebuild WebP variants and enrich image markup only
python3 build_seo_guides.py         # rebuild only localized guides, sitemap and robots.txt
```

### Newsletter signup

The home page embeds Brevo's hosted subscription form. Its URL lives in one
constant in `build.py`:

```python
NEWSLETTER_FORM_URL = "https://….sibforms.com/v2/serve/…"
```

Brevo handles single opt-in, the automatic confirmation email, unsubscribe records and abuse protection. The
static site contains no Brevo API key. Update the form in Brevo, replace the
hosted URL only if Brevo issues a new one, then run `python3 build.py`.

### Data checks

The Notion exporter writes a temporary snapshot and the deployment validates it
before publication. An invalid or unavailable source never replaces the last
working preview. Participation status is explicit: DNS is not a participation;
DNF and DSQ are participations even when no time is recorded.

| Check | What it would have caught |
| --- | --- |
| placing contradicts points · points off the ladder | the standings summed the placing column as if it were points, inverting the whole table for months |
| results with no profile | 9 riders scored points with no row in `Profils`, so they had no page and shifted everyone behind them |
| no / duplicate Instagram handle | the equipment tabs are keyed on the handle, so a missing one means a rider page with an empty setup |
| team spelled several ways | one accent split a team's total across two rows of the standings |
| same placing twice | two riders were both credited 8th at Loudenvielle |

Warnings don't block: a round label still in French, or a brand used both bare
and with a model — the latter makes the equipment leaderboards rank a brand
against its own models, so the category leader shown can be wrong.

Men and women score on **different ladders**, diverging below 6th place. Both
live in `validate.py`; deriving a position with the wrong one is how the
placings and the points drifted apart in the first place.

The full build automatically runs the SEO guide generator last, after every
rider, equipment and editorial page exists, so the sitemap stays complete.

Never hand-edit `index.html`, `riders.html` or files in `riders/` — they are
overwritten on every build.

### Automatic OVH deployment

Production uses OVH shared Web Hosting. `Update Preprod` refreshes the protected
preview from Notion and Google Drive. `Preprod to Prod` is manual-only and
promotes the exact revision, data snapshot and image snapshot already validated
on preproduction to `/home/ridersi/www`.

Legacy VPS/systemd examples under `deploy/` are not part of the active OVH
shared-hosting architecture.

### Protected preproduction

The `preprod` branch is built with `RF_BUILD_ENV=preprod` and deployed by
`.github/workflows/deploy-preprod-ovh.yml` to a directory that must be separate
from `/home/ridersi/www`. Its canonical origin is
`https://preprod.ridersfanatics.com`.

Competition publication state lives in `data/competitions.json`. Production
builds include only `published` records. Preproduction builds also include
`draft` records, add `noindex` metadata, generate a blocking `robots.txt`,
disable Brevo signup and omit the PHP contact endpoint. Apache Basic Auth is
applied with `deploy/preprod.htaccess`; credentials and the absolute htpasswd
path live only in the GitHub `preproduction` environment.

Required preproduction secrets are `NOTION_TOKEN`,
`GOOGLE_DRIVE_SERVICE_ACCOUNT_JSON`, `OVH_SFTP_HOST`, `OVH_SFTP_PORT`,
`OVH_SFTP_USER`, `OVH_SFTP_PASSWORD`, `OVH_REMOTE_DIR`, `OVH_AUTH_FILE`,
`PREPROD_BASIC_USER` and `PREPROD_BASIC_PASSWORD`. The remote directory must
never be `/home/ridersi/www`. Set the preproduction environment variable
`GOOGLE_DRIVE_IMAGE_FOLDER_ID` to the root image-library folder and share that
folder with the service account email as Viewer. The Drive scope is read-only.
Add `OVH_SFTP_KNOWN_HOSTS` to both deployment environments with the verified
OpenSSH known-host line for the OVH server. Until it is configured, the
workflow remains backward compatible but emits a security warning.

Production OVH credentials should live only in the GitHub `production`
environment, using a dedicated SFTP account restricted to `/home/ridersi/www`.
Preproduction should use a different account restricted to its preview path.

### Read-only Notion and Google Drive sync

Preproduction checks Notion and the Drive image library every 15 minutes. Both
integrations are read-only. The workflow imports rider portraits, action shots
and equipment images, then compares the generated data and image hashes with
the versions already on OVH. An unchanged snapshot is not redeployed, and an
invalid or unavailable source cannot replace the last valid preview.

Every image found recursively under the configured Drive folder is also
mirrored under `assets/img/drive-library/` for publication, even when its folder
or filename does not yet match a rider, equipment item or competition component.
Recognised `PPRiders`, `PictureRiders` and `Equipment` folders additionally feed
the site's normal optimized image paths.

The Notion public API queries data sources rather than UI views. Equivalent
filters are therefore enforced in `scripts/sync_notion.py`. Add the integration
secret as `NOTION_TOKEN` in the GitHub `preproduction` environment and share
the RidersFanatics database plus each related source with that integration.

Production is never deployed by a timer or by a push. It is promoted manually
from the latest successful preproduction snapshot. The same workflow can
restore a retained, checksum-verified production snapshot when the operator
selects `restore`, supplies its workflow run id and types `RESTORE`.

## Photos

The authoritative photo library lives in the configured shared Google Drive
folder. The preproduction workflow mirrors it read-only before importing,
resizing and matching its files into the generated site paths. For a local
already-synchronized copy, run:

```bash
python3 import_images.py
```

| Library folder | Becomes | Used for |
| --- | --- | --- |
| `PPRiders/@handle.jpg` | `assets/img/riders/{slug}.jpg` (400×400) | avatars on the rider grid |
| `PictureRiders/@handle.jpg` | `assets/img/riders-action/{slug}.jpg` (max 900px) | hero on the rider detail page |
| `Equipment/{Category}/Brand;Model.webp` | `assets/img/equipment/{cat}-{brand}-{model}.jpg` (max 600px) | thumbnails on rider pages + Best Equipment carousel |

Riders are matched on the Instagram handle already in `riders.json`, so messy
filenames (trailing space, capitals, missing `@`) still resolve. Equipment is
matched per category against the products actually used, and the imported
filename is derived from the *product*, so the site's lookup stays exact.

Options:

```bash
python3 import_images.py --report     # what would match, writes nothing
python3 import_images.py --force      # re-process files already imported
python3 import_images.py --no-build
```

The run ends with the list of products still missing a photo, giving the
filename to add and the category folder to drop it in.

### Frame reveal
On a rider page the frame is the centrepiece of the chassis composition and
gets a three-stage reveal when scrolled into view: a line drawing traces
itself, becomes a pencil sketch, then resolves into the photo. A replay
button appears in the panel corner afterwards.

Both extra layers are **derived from the frame photo** by `import_images.py`
(needs `opencv-python`; the step is skipped with a notice if it's missing):

```
assets/img/equipment/reveal/{frame-slug}-sketch.png   dodge-blend pencil render
assets/img/equipment/reveal/{frame-slug}-draw.svg     Canny contours as self-drawing paths
```

Add a new frame photo and rerun `python3 import_images.py` — both layers are
generated automatically, no hand-authored assets. Use `--force` to regenerate
after tuning. Frames without these files simply show the plain photo, and the
whole sequence is disabled under `prefers-reduced-motion`.

### Why the category is in the equipment filename
28 products share a brand and model across different categories — "Shimano
Saint" is a brake lever, a crankset, a derailleur *and* a pedal. Without the
category prefix they would all collide onto a single photo, so the site would
show a pedal where a derailleur belongs. This is also why the library's
category folders must stay: flattening them into one directory would throw
away the information that keeps those products apart.

### Missing-image report
Do not add production photos directly to generated `assets/img/...` paths.
Add them to the shared Drive library so the next preproduction synchronization
can preserve the source file and regenerate every derivative consistently. To
see every filename the build is looking for from an already-synchronized copy:

```bash
python3 build.py --missing-images
```

Missing images remain non-blocking: rider pages fall back to the available
rider picture or initials, while equipment cards omit an unavailable image.
The deployment health guard prevents an abnormal drop in the total Drive or
published-image counts from reaching production.
